## 工程1：作業対象と自動処理の安全な整理（最優先）

1. 作業ツリーの差分・未追跡ファイルを一覧化し、最新版へ含めるソース・リソース・文書を決める。既存の修正を巻き戻さない。
2. `scripts/run_device_tests_and_save.py`を修正する。現在は対象パッケージと起動ActivityがViewerのままで、既存Viewerをアンインストールする処理があるため、**修正・回帰検証前は実機で実行しない**。
3. 正しいUtilityのパッケージ／Activity、端末の明示指定、既定は情報収集のみ、Play版保護、Debug試験の分離、クリーン試験の明示指定へ変更する。失敗時の自動削除はしない。
4. 合否判定をPython試験だけに依存させず、インストール・起動・単体・端末試験の失敗／未実施も反映。端末の実インストール版を取得し、検証一覧を自動で「問題なし」にしない。
5. `scripts/update_docs_and_listings.py`には過去の版番号の一括置換が残るため、既定を検査のみ・明示した現在版だけ更新する方式へ変更。Utilityのヘルプキーやmetadata_*.txt形式に合わせる。タグ自動生成は実行しない。
6. 署名設定の未指定時に固定の値へフォールバックする処理を見直す。既存の登録済み鍵を維持し、秘密値はローカル設定からのみ取得。Release署名が必要なときは設定不足を明確に失敗させ、署名情報なしのDebug CIは動作させる。

完了条件：別アプリや利用中の実機を変更しないこと、試験失敗・未実施を合格にしないこと、版履歴を変えないことを回帰試験で確認。実機の自動試験は専用エミュレーターから開始。

## 工程2：サンプルPDFとデータ・機能の整合

- 参照先不一致14件（スペイン語・イタリア語・ポルトガル語・ベトナム語・インドネシア語・フィリピン語・ネパール語の第1・2話）の正しいファイル名・取得URL・内容・ライセンスを照合する。`_2_`の有無や`fil`／`tl`を含め、実ファイルに合わせる。
- 配布正本を明確にし、カタログ、ローカル検査対象、Webの配布リンク、ハッシュ記録を同期する。テストを通す目的でPDF本体を無条件に上書きしない。
- `testdata/`にはGit除外指定がある一方、一部は既存の追跡対象。計画時のテストは未配置時に配布ファイル自身と比較してしまう。CIで自己比較の合格にならないよう、検証済みのハッシュ一覧や追跡対象の正本に基づく比較へ改善する。
- カタログ外の未追跡PDF、負荷試験用PDF、個人素材をまとめて公開しない。配布対象とテスト専用素材を選別する。
- ソートの初期値・第1話順／最新話順、保存・再起動、言語絞り込み、同話数の言語名順、ダウンロード／削除後の順序を検証する。14言語へ各3話を増やすなどの機能拡張は別判断にし、現在の33件を理由なく変更しない。

完了条件：カタログ対象の取得URLが有効で、内容とハッシュが整合。カタログ・ソートの意味ある試験がCIでも成功する。

## 工程3：翻訳・表示・公開情報の仕上げ

- `preBundleDocumentationCheck`の正規表現によるキー比較を実リソースへ照合し、非翻訳指定・複数形・空文字も確認できる検査を併用する。
- ハードコード文言、ヘルプ、README日英、docs/*.html、store_listing/metadata_*.txt、アイコン・掲載画像を現行機能へ同期。未公開の新候補を公開済みと書かない。

完了条件：欠落・意味を変える未翻訳・操作不能がない。自動診断と実機手動確認を区別して報告する。

## 工程4：ビルド・Lint・PDF編集の回帰検証

JDK21とプロジェクト指定SDKを使用し、Debugビルド、単体試験、Debug/Release Lint、preBundleDocumentationCheckを実行する。ReleaseのR8／リソース縮小は有効な成果物で検証し、今回必要な修正以外の全面リファクタリング・依存関係の大型更新は分離する。

必須確認：

|分野|確認する内容|
|---|---|
|入力|端末PDF・クラウド・他アプリから開く、パスワード付きPDF、失敗時の復帰|
|閲覧|右／左綴じ、単ページ／見開き、表紙、拡大縮小、回転、目次・検索|
|編集|ページ並替・回転・削除・白紙追加、複数選択、適用とキャンセル、操作後の表示整合|
|保存・出力|別名保存、必要な保存方式・セキュリティ／メタデータ設定、出力PDFを再度開いてページ数・順序・向き・内容を確認|
|画像・フォルダ|既存の画像／フォルダからPDF生成機能について、対象選択、並び順、生成物の再読込|
|耐久性|大容量PDF、連続編集・切替、キャンセル・復帰、保存失敗。元の個人PDFではなく試験用コピーを使う|
|応援・更新|Playの実価格・購入済み権利・再照会、更新前後の設定保持。テスト購入はライセンステスター設定とテスト決済表示を確認|

Lintエラーと単体失敗は解消する。残る警告は依存関係・実際の呼出経路・R8の削除結果・端末試験に基づいて判断し、件数と理由を記録。SDK／Billing更新がConsole要件で必要なら、別途互換性・購入回帰まで行う。特に保存・暗号化機能を持つUtilityでは、Viewerの結果を流用しない。

## 工程5：版番号・署名付きAABの確定

1. Consoleの全トラック／全バンドル最大番号と署名証明書を読み取り、版番号を確定。
2. `store_listing/changelog/v<版>/`の既存形式に合わせて、配信中22からの累積ノートを作成。掲載済み言語と実際の対象に合わせ、各言語の上限・空文・仮文を検査する。
3. 既存鍵で署名付きbundleReleaseを作成。アプリID、versionName／versionCode、全署名、証明書、AAB構造、R8 mapping、SHA-256を記録。
4. 同じAABから生成したRelease APKで、工程4の重要な閲覧・編集・保存・スクロールを確認する。試験のために製品向けR8規則を緩めない。
5. ソース・必要リソース・バージョン・ハッシュを固定。以後ソースを修正したら別成果物として再検証し、アップロード済み番号は再利用しない。

完了条件：Consoleへ登録するAABが、検証済みソースと同一で、既存アプリへ更新可能な署名であること。

## 工程6：クリーンなコミット候補・CI・公開Pages

- 必要な未追跡ソート定義、plural、PNG・適応型アイコン、監査スクリプトを含めてコミット候補を作る。依頼プロンプト・鍵・local.properties・個人PDF・一時ログは除外。
- コミット候補から署名情報なしのクリーンなコピーを作り、CIと同じビルド・Lint・単体・文言／Web検査を実行。ローカルのSDK絶対パスやtestdataの偶然の存在に依存しないことを確認。
- ローカルコミットをAABと対応付け、実行範囲の指示を受けてpush。該当コミットのGitHub ActionsとPagesデプロイが成功するまで不具合を解消する。
- 公開URLで画像・言語切替・サンプル配布・ヘルプ・プライバシー・Play導線を確認。別アプリの成功したCIや、古いコミットの成功を流用しない。

完了条件：最終候補と対応するコミットのCI成功、公開資料の整合が確認できる。
